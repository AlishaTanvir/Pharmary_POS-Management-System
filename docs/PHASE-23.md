# Phase 23 - Recorded historical report classification

Authorized as the next sequential phase after Phase 22. Source: 0.23.0-dev.1. Verification date: 24 November 2026. Status: software complete within the documented recorded-history scope. Field acceptance and production approval remain pending.

## Policy and preserved behavior

Operational reports previously combined historical movement quantities with current category membership and lifecycle labels. That mode remains the default, explicitly CURRENT_CATALOG. It is not relabeled as historical evidence. Dashboard aggregates, stock cards, existing financial postings and existing count-sheet category snapshots retain their established semantics.

The new AS_OF mode applies to valuation, expiry exposure, batch movement reconciliation, sales invoices and velocity. It uses recorded category trees/assignments, medicine names/generic/form/activity/reorder levels and batch status/expiry at a single requested cutoff. Quantities, sales and movement demand stop at that same cutoff. Period opening remains before the Pakistan-local from-date. Classification is at the report cutoff, not separately attributed at each transaction's event time. Audit exceptions do not have product classification and reject AS_OF.

The cutoff defaults to the end of the through-date in Asia/Karachi, capped at generation time for today. An optional ISO timestamp must fall on that through-date in Pakistan and cannot be future dated. The UI accepts a Pakistan-local time with optional milliseconds. API metadata returns the actual applied UTC timestamp. AS_OF does not accept a future through-date. The time basis is the database transaction timestamp, at millisecond precision; all snapshots written in the same transaction share a logical time. A sequence orders multiple versions within that timestamp, and the final committed version is selected. This is not exact commit visibility, inferred external effective dates or a point-in-time database backup.

## Capture baseline and unknown history

Migration 020 locks the category, medicine and batch source tables while it copies a baseline and installs capture triggers in one transaction. The baseline marks when trustworthy continuous application capture begins. Existing current values are copied only at that transaction's timestamp; they are not backdated to when a product was first sold or created. Financial invoices, allocations, movements, unit costs, journals and original count sheets are not rewritten.

Append-only category_classification_history, medicine_classification_history and batch_lifecycle_history record inserts, relevant updates and deletions. The classification_capture marker records the start/version. Migration 020 was applied successfully to the retained development database after isolated checks, with no financial source rewrites. Database triggers cover all source writers, including catalog CSV, shared catalog publication, category creation/reparenting/assignment, activation changes, receiving, returns, transfers and lifecycle maintenance. Quantity-only updates do not create redundant lifecycle snapshots. A failed transaction rolls back both its source mutation and its captured history. Source identities cannot silently move across branches. History cannot be updated/deleted or assigned a caller-chosen earlier timestamp. Writers crossing the migration boundary may need to retry if their transaction predates the capture baseline; deploy using the established quiesced-upgrade procedure.

Before the baseline, a legacy identity supported by old sale/movement evidence remains UNKNOWN. This is different from a captured null category, which is known UNCATEGORIZED. Unknown names/forms/expiry are not filled from the current catalog and presented as historical facts. Legacy product rows use an explicit unknown label and stable medicine ID; use that ID to filter them. Newly captured identities are excluded before their recorded insertion. Historical category options and descendant membership come from the tree at the selected cutoff; a currently existing category that was not observed then cannot be used as if it existed historically.

Existing audit events and immutable count-sheet category snapshots remain available in their original workflows. They are not discarded, nor treated as a complete continuous classification history. No incomplete audit chain or isolated count observation is used to invent the missing legacy series.

## Report semantics and reconciliation

Captured category paths reflect historical names and parent links. Later renames, reparenting, assignment changes, medicine edits or deactivation do not replace those captured values for an older cutoff. Product reports include inactive identities where their stock/transactions remain relevant and disclose captured activity separately. Historical classification does not alter invoice amounts or stock balances.

Valuation and expiry keep signed physical quantities derived from the movement ledger and recorded immutable cost. They expose observed_status_as_of, effective_status_as_of, expiry_as_of, category capture state, activity and history sequence references. A captured AVAILABLE batch whose expiry is earlier than the report date is effectively EXPIRED, even if the maintenance job had not yet relabeled it. Other blocked lifecycle states remain explicit. Unknown legacy expiry/status rows remain included as unknown exposure, not silently treated as safe or excluded from expiry review.

Movement reports preserve opening + incoming - outgoing = closing. Millisecond truncation is used for both movement cutoffs and captured classification so a status change and its stock movement in the same transaction are included together at an exact captured instant. Sales remain whole matching invoice totals, not category-attributed revenue. Matched classification metadata identifies eligible medicine identities; returns_as_of_paisa is cumulative for those invoices through the cutoff, not period net returns. Existing CURRENT-mode lifetime_returns_paisa retains its original meaning.

Velocity separates gross units sold and returned within the selected period and exposes as_of_physical_available plus unknown_status_base. Availability means physical units with captured AVAILABLE/unexpired batch status, before reservations; it is not reconstructed sellable availability. Current cashier names and fixed supplier identities remain descriptive references. Quantities use central recorded movement/posting times; unsynchronized offline events and historical reservation balances are not reconstructed.

## CSV, display and evidence limits

AS_OF CSV uses a normal header, one record_type=METADATA row and then record_type=DATA rows. Metadata includes the applied cutoff, capture start, category scope/basis and matched unknown counts, even for an empty report. Count and totals apply only to DATA rows. CSV data is built from the same result rows returned to the screen. Numeric values remain integer paisa/base quantities; negative numeric fields remain numeric, and dangerous text prefixes are escaped for spreadsheets. Existing CURRENT CSV structure is preserved.

With unchanged filters, AS_OF export reuses the displayed cutoff and updates the screen with the exported response. Ordinary later transactions cannot replace captured versions at an older cutoff. A transaction that started earlier but commits later can become visible in a later report at that logical recorded time; descriptive staff references can also change. Consequently this is a repeatable recorded-time query, not an immutable saved report or exact historical database snapshot. Preserve an exported file independently when fixed evidence is required. Bank closing evidence remains a separate immutable workflow. PDF/print includes the basis/coverage notice and selected result rows.

## API, access and recovery

POST /api/reports/operational accepts classification_basis CURRENT (default) or AS_OF and optional classification_at with an explicit timezone. category_id UNKNOWN is allowed only for AS_OF; known Uncategorized remains separate. Existing category/supplier/product/form/cashier behavior applies where appropriate. GET /api/reports/options accepts the same basis/time selection with to=YYYY-MM-DD and returns historical category/form choices, capture start and applied cutoff. Current supplier/cashier reference choices remain branch scoped.

No new route or permission is introduced. Both endpoints retain reports permission and the existing session/CSRF boundaries. Cashiers cannot inspect/export classification history through them. Repeated-read transactions prevent mixed report snapshots during one request. Export audit records include the basis, applied cutoff, scope, coverage and row count. Current inventory remains 160 declared routes, 147 session routes, 86 CSRF checks and 545 denied-role checks.

Restore verification checks the capture marker/time bounds and that the latest captured category, medicine and batch states agree with retained sources, including deletion evidence. Earlier backups without the capture tables retain their established verification path. The check is not an external signature or validation of unavailable pre-baseline history. The frozen Phase 5 release remains unchanged; use a compatible app with migration 020 for subsequent posting/capture.
